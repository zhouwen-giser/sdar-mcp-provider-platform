# G4-P3-B01 — Prove Worker-to-Runtime production lifecycle end to end

## Phase

`P3`

## Dependencies

G4-P2-B03

## Objective

用真实 PostgreSQL、正式 PMS API Composition、正式 Worker Composition、仓库固定 PM2、built Runtime 和 Mock Provider Adapter 证明完整生产生命周期与恢复行为。

## Allowed Paths

package.json

## Forbidden Paths / Actions

```text
New product feature
New Migration
Fake PM2 or in-memory repository
Manual database state advancement
Direct PM2 CLI
Real-resource certification claims
```

## Required Work

1. Add `test:worker-pm2-production` and a fail-closed gate script.
2. Test fixture must use:
   - real PostgreSQL for PMS;
   - real provisioned Runtime database/role;
   - real PMS migrations and Runtime migrations;
   - production PMS API Composition;
   - production Worker Composition;
   - pinned PM2 JavaScript API;
   - built Runtime fixed release entry;
   - real local Mock Provider Adapter;
   - secure temporary Credential/Secret files.
3. Drive the path through public API intent where possible:
   Provider/config/database profile → RuntimeDeployment create → Worker claim → DB prepare → migrations → bootstrap/secret → PM2 start → health → registration/heartbeat → discovery → Catalog → Registry → ACTIVE.
4. Verify Registry can resolve the active Runtime and a controlled SDAR consumer can reach it without bypassing Registry authority.
5. Fault scenarios:
   - Runtime SIGKILL → DEGRADED/recovery → ACTIVE;
   - Adapter unavailable → not ACTIVE;
   - Provider identity mismatch → failed/degraded, never ACTIVE;
   - Worker stopped → Runtime remains running;
   - PMS API stopped → Runtime remains running;
   - Worker restarted → scheduler/reconcile resumes;
   - Config revision changed → one controlled PM2 restart;
   - stale lease/fence cannot complete newer work.
6. Cleanup all Runtime processes, PM2_HOME, temporary DB roles/databases and files after the test; cleanup may use the production PM2 Bridge, not CLI.
7. Produce redacted Evidence with transition timeline and exact versions.

## Acceptance Criteria

- Deployment reaches ACTIVE only through the complete production path.
- Runtime crash and config drift recover correctly.
- Worker/PMS outage does not stop Runtime.
- Identity/Adapter failures never produce ACTIVE.
- Scheduler and fencing recovery are demonstrated.
- No PM2 CLI, Fake repository or manual status mutation is used.
- Cleanup leaves no `sdar-runtime-*` process, temporary database or Secret file.
