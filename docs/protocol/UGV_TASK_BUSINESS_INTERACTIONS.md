# UGV task business interactions (`1.0-rc2` development)

`packages/vehicle-provider-core/src/task-business-interaction.ts` is the canonical schema and transition/guard source. The generated JSON Schemas are in `protocol/task-business/v1/interaction.schema.json`. Observed UGV visual lock Actions are now projected locally from mission-bound device status. Runtime `tasks/update` accepts a synthetic business Input through its trusted role and durable transport in local tests, but the UGV Provider has no real Required Input producer or decision handler. Runtime now also exposes a conditional public Intervention method backed by its durable Task command lane. A local synthetic Profile and mock Adapter exercise that transport; the selected UGV Profile remains read-only and has no accepting Intervention handler.

An Action first observed already active may omit `requestedAt` only for a device actor with `device_automatic` or unknown trigger origin. It must have an actual `startedAt` observation. This records the first known active state without inventing a prior request time. A `requested` Action still requires `requestedAt`, and later revisions cannot backfill or change the request/start time. The UGV source currently does not qualify an automatic trigger, so its Action uses `triggerOrigin: unknown` and the recon Profile keeps automatic visual lock qualification disabled.

## States

| Object                   | Allowed transition from an active state                                     | Meaning                                                                                                    |
| ------------------------ | --------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Action `requested`       | `requested`, `active`, `failed`, `cancelled`                                | A requested visual lock is not an established lock.                                                        |
| Action `active`          | `active`, `completed`, `failed`, `cancelled`                                | Loss of visual lock ends as `failed` with `VISUAL_LOCK_LOST`, never normal completion.                     |
| Required Input `pending` | `pending` metadata revision, `answered`, `declined`, `cancelled`, `expired` | It is blocking and corresponds to an existing execution wait condition. Terminal requests cannot reopen.   |
| Intervention `available` | `available`, `submitted`, `expired`, `withdrawn`                            | It is optional and `blocking=false`; availability alone never changes Task state.                          |
| Intervention `submitted` | `applying`, `failed`, `withdrawn`                                           | One command was accepted. The receipt does not mean the plan changed.                                      |
| Intervention `applying`  | `applied`, `failed`, `withdrawn`                                            | `applied` requires a business result reference and real adoption confirmation in the later implementation. |

All changes increment the object revision by one. Terminal states do not reopen. A Required Input keeps its `requestId` and non-reusable `requestKey` for its lifetime. Changing its input schema, subject binding, responder, deadline or policy requires cancelling it and publishing a new request/key. An Intervention instance is also single use: changing its plan basis, input schema or target references requires a new instance. Invalid new command content is rejected before the command ledger claims the entry; the available entry stays unconsumed. The command registry must first look up an existing `commandId` for idempotent retries, then run the new-command preflight.

## Guards and authority

In the negotiated semantic mode, a Required Input response checks `expectedRequestRevision` and the current lock session or Artifact binding. A non-blocking intervention checks `expectedInterventionRevision` and `expectedEffectivePlanRevision`. Trajectory/footprint changes may advance Context revision without invalidating either command. An actual replacement of the decision request, target binding or effective plan conflicts. The explicit `legacy_strict` mode keeps the old `expectedContextRevision` guard; deployed callers must negotiate it rather than silently receive a weaker check.

Input response command JSON contains no `respondedBy` or `requestedBy` field. The Runtime must supply a verified principal from its authorization context; a caller's claimed `user` actor is not proof of human approval. `requiredResponder=user` accepts only that verified human principal. The pure preflight helper tests the supplied principal but cannot establish its provenance until Runtime wiring.

The partial Runtime intake guard now derives `verifiedResponder` only from a signed HS256 JWT `actor_type` claim or the authenticated proxy's `x-sdar-actor-type` header (`user`, `agent`, or `operator`). Development and anonymous modes never set this field. For `tasks/update`, a persisted business `elicitation/create` request carries `_meta["io.sdar/taskBusiness"]` with `schemaVersion`, `requestKey`, `inputType`, and `requiredResponder`. The Runtime checks that metadata against the locked request, the operation's declared input types and `decisionMode`, and the verified caller role before accepting a new response. A `user_required` Profile permits only a verified user. `actorId` is copied from the authenticated subject for audit; a request body cannot supply it as authority. The trusted proxy must strip caller supplied `x-sdar-actor-type` along with subject and tenant before setting its own values. This guard is locally verified with a named synthetic test proxy; the selected UGV Profile still advertises no business RequiredInput, and no Provider decision execution is claimed.

For a business request, the Runtime stores the accepted frozen response with its server verified responder in a versioned internal inbox envelope, then promotes the ordinary response and responder map into one durable UPDATE command. The private Adapter `McpTaskInputResponse.verified_responder` field forwards that map through the generic `UpdateExecution` reply route. Legacy/nonbusiness inbox rows and wire replies retain their previous shape. The local PostgreSQL plus mock Adapter test proves storage and transport only; the UGV Runtime still rejects non-fire replies until its decision handler can use the provenance and current lock session.

The locked PostgreSQL inbox transaction admits a new business answer only while the Task is `INPUT_REQUIRED` and has no cancellation or stop request. If Task control changes after inbox acceptance but before command promotion, promotion supersedes the open request and marks the business answer `IGNORED` when the Task has left input wait, without producing an UPDATE command. For an already assigned business UPDATE, the dispatcher rechecks the locked Task and verified request before an Adapter call. After an accepted Adapter reply it rechecks again under the Task lock: a superseded request exhausts the old command without retry, preserves the Adapter Ack and records that the RPC succeeded. This does not reverse an already dispatched physical effect; the real UGV decision handler must validate its current lock/session at the effect point. A nonretryable Adapter rejection records a rejected command without directly failing the whole Task. Frozen nonbusiness replies retain their earlier rules. Provider-side subject/session invalidation and publishing an expired Input with its `onExpire` outcome still need the qualified UGV decision handler and lifecycle work.

When a UGV Required Input has `deadlineAt`, its execution snapshot now carries that value in `_meta["io.sdar/taskBusiness"]`. Runtime validates its time format, then the locked `tasks/update` inbox transaction uses PostgreSQL `clock_timestamp()` to reject a new answer at or after the deadline before inserting a row. For a business Input already in the inbox or marked answered, an identical answer is a duplicate after caller validation; different answer content returns `INPUT_ANSWER_CONFLICT`. The inbox case also checks the current Task control state. This duplicate check applies to business requests without a deadline, too. Legacy Input reply semantics stay unchanged. A timed-out request does not become an `expired` business object or lift Task input wait until the qualified Provider lifecycle publishes that transition and performs its `onExpire` policy.

A resolved Required Input records `resolvedAt` at or after its immutable `requestedAt`. The Provider contract rejects a response or expiry whose recorded resolution predates the request. Action, Input and Intervention timestamp ordering uses the full ISO fractional precision, including values within one millisecond. This check does not turn an accepted reply into evidence that its physical follow-up action completed.

`cancel` is a response to one Required Input. It selects `onDismiss`, such as `release_and_resume_scan`, `end_observation`, or `reissue_request`; it never invokes `tasks/cancel` by default. `decline` uses `onDecline`, expiry uses `onExpire`, and an accepted answer waits for its actual business result. Those policies must be implemented through the existing execution state path, without automatically lifting an unrelated human pause. Optional plan edits use Intervention, never a Required Input or `WAITING_INPUT` merely because an edit is possible.

An `answered` or `declined` Input revision, and a `cancelled` revision carrying a caller's `cancel` response, records `responseCommandId` and resolves the previously active request. Memory and PostgreSQL require that exact command ID to have been admitted as an Input reply for the same request key in the bound Provider scope before committing the new Context/object version. The admitted command also carries `responseHash`, a SHA-256 digest of the canonical reply action/value. The committed Input response must match that digest, and a terminal command update cannot alter it. The command may later be rejected because the requested local action failed; that does not erase the fact that the caller answered. A system cancellation may publish `cancelled` without a response or command ID, while `expired` remains a separate no-response transition. Neither a reply fact nor a command receipt proves a physical effect.

`TaskBusinessCommandService` now uses the Store ledger for both Input responses and Interventions. It requires a bound Provider execution scope, a verified Runtime responder context, and a positive Runtime command sequence. It validates the typed request and computes SHA-256 from canonical semantic fields except `commandId`; arrival time and display text are not part of the digest. A retry looks up the existing command before checking current entry state, then returns its persisted accepted/result record. A changed request under the same ID conflicts. A new request checks its semantic or explicitly negotiated strict guard, then claims an entry and Runtime sequence in the Store. Native migration `031_task_business_command_fences.sql` adds unique entry and Runtime sequence fences; the shared owner handoff includes equivalent indexes. Physical device calls must happen after the claim transaction, with the terminal result saved by `commitBusinessChangeSet`.

The Memory and native PostgreSQL claim paths also allow only one `accepted` Intervention command in the same bound Execution scope across different entry IDs. A second new command returns `BUSINESS_CHANGE_IN_PROGRESS`; retry of the original ID still returns its persisted record, and a terminal rejected command releases this single-flight guard. The claim transaction rechecks the entry's `effectivePlanRevision` against the current Context so a plan switch after preflight returns `PLAN_REVISION_CONFLICT` without reserving a command. This is a local ledger invariant. It does not create a replacement Intervention after real adoption or qualify the absent UGV running replan source.

The generic `TaskBusinessCommandService.submitIntervention` now uses an opt-in Store claim path that commits the `accepted` command, a new `submitted` Intervention version, the next Context revision and two typed `vehicle.business` source events in one Memory or native PostgreSQL transaction. The Context's active Intervention ref points to that submitted version, while the effective plan and active route stay unchanged. The `BUSINESS_EVENT.contextDelta` carries complete active refs and the unchanged plan revision; `INTERVENTION_CHANGED` names the new version and its predecessor. A same-ID replay returns the original command without another Context revision or source event. The lower-level claim method remains available without submission publication for synthetic fixture construction. This generic admission boundary does not call a device or claim plan adoption. The selected UGV handler still declines `ApplyIntervention` and its read-only Profile does not advertise an accepting entry.

When a claimed Intervention command is committed as `applied`, the Memory and native PostgreSQL Store require the same changeset to publish a matching terminal Intervention version with the accepted command ID and identical result refs. Publishing a terminal `applied` Intervention without its command result is also rejected. Those refs must be present in the new Context, with at least one new result object; the completed entry cannot remain active. For plan-changing types, the Context effective plan revision must advance exactly once from the entry's old plan basis. An isolated route object or receipt cannot mark the command applied. This is an internal fact-consistency fence; only a qualified device adoption signal can justify the Provider producing those facts. The selected UGV handler still returns a negative Ack and never publishes an applied Intervention.

The applied result also requires source events in that changeset: `INTERVENTION_CHANGED` for the terminal entry, a `BUSINESS_EVENT.contextDelta` carrying the new effective plan revision and complete active refs, and the matching typed change event for each newly written result object. The native PostgreSQL Store commits these events with the Context and command in one transaction; direct eventless `commitChangeSet` rejects an applied result. The Memory Store enforces the same event set for its local fixture. These events make the facts visible to a public SSE consumer, but they do not themselves prove a device accepted the plan.

For negotiated `legacy_strict` Input and Intervention commands, the Store also rechecks the caller's `expectedContextRevision` inside the claim fence. A Context change between Provider preflight and claim returns `CONTEXT_REVISION_CONFLICT` without a ledger record. Semantic guards continue to permit unrelated Context revisions while checking their request or plan basis. Existing command IDs replay before this new-command recheck.

Before that claim, the Provider also validates an accepted Input value against the persisted Required Input `inputSchema`, and an Intervention's `input` against its persisted Intervention `inputSchema`. A malformed schema or mismatched value fails closed with a distinct reason; neither reserves a command ID nor consumes the entry. Decline and dismiss replies do not need a decision value. This is local Provider admission validation; it does not qualify a native lock session, publish a request, or apply a plan change.

The common business Store also compiles each Required Input or Intervention `inputSchema` before its Context/object changeset can commit. A malformed published entry rolls back with its Context and source events, so consumers cannot discover an entry that is impossible to answer under the declared schema. This is enforced in Memory and native PostgreSQL Store paths; the selected shared GOWM installation remains separately unverified.

A new Input answer at or after `deadlineAt`, or Intervention at or after `validUntil`, now fails before a command is accepted. Memory Store repeats the time check during its claim; PostgreSQL reads `clock_timestamp()` under the same scope advisory transaction lock used for Context/command claims. Existing command IDs still replay their original record before the new-command time check. Rejecting a late command does not by itself create an `expired` object revision or execute `onExpire`; the qualified UGV lifecycle producer must do that separately.

The existing native `tasks/update` accepts an `inputResponses` map. The Adapter Proto now reserves an additive `business_input_command` field on `UpdateExecution` and a distinct `ApplyIntervention` RPC. The common gRPC server dispatches these fields to optional Runtime handlers and returns `UNIMPLEMENTED` while they are absent. UGVB-032/034 will bind the input path and SDK `RespondTaskInput` to one decision handler, with request key/semantic revision carried by the negotiated business profile.

The conditional public `io.sdar/taskBusiness/interventions/apply` method accepts the flattened `RuntimeInterventionCommand` fields and `_meta` through POST `/mcp`. It requires the Tasks and TaskBusiness client capabilities, `mcp-name: <taskId>`, an authorized persisted Task/Execution, an Operation Profile with `interventionApply` and a declared type, and a verified JWT or trusted proxy responder. For a new `commandId`, Runtime locks the Task, allocates its normal command sequence, persists an `INTERVENTION` command and observation, and returns `receipt {commandId, commandSequence, commandState, durablyAccepted, businessApplied, duplicate}`. Reusing that ID with changed semantic content returns `COMMAND_ID_CONFLICT`; a different ID while any Task command remains active returns `BUSINESS_CHANGE_IN_PROGRESS`. A safe stop supersedes queued Intervention. The dispatcher rechecks Task running state before private `ApplyIntervention`, retries uncertain delivery, and blocks later new changes for reconciliation if delivery is exhausted. The receipt's `durablyAccepted: true` means **Runtime queue acceptance only**; `businessApplied` remains `false` even after the mock Adapter acknowledges dispatch. It is not Provider ledger acceptance, adopted plan, device effect, or an Intervention `applied` object. See the synthetic HTTP/PostgreSQL/gRPC evidence in `.codex/SMPP_UGV_Business_Feedback_Codex_Goal_v1.0/reports/P6_PUBLIC_INTERVENTION_DURABLE_WIRE.md`.

The selected UGV Provider handles the private RPC with a terminal negative Ack after verifying the persisted Execution identity. A prior command-sequence Ack replays first. A new request must carry a schema-valid Runtime Intervention command bound to that Task/Execution and a structurally trusted responder; malformed or mismatched requests receive an unpersisted denial and cannot reserve the sequence. A RUNNING Task then returns `UGV_INTERVENTION_NOT_SUPPORTED`; a Task outside RUNNING returns `UGV_INTERVENTION_TASK_NOT_RUNNING`. This denial is persisted by sequence for replay. It prevents a stale Runtime capability snapshot from treating a known unsupported UGV operation as an unknown gRPC delivery. It never calls a device tool or accepts an Intervention into the Provider business ledger. The UGV Profile still advertises `interventionApply: false`; actual acceptance and replan need the qualified device capability and a later handler.

`UpdateExecution` now also offers an operation-aware `updateInput` hook in the common vehicle gRPC server. The UGV Runtime checks the persisted Execution identity before routing both frozen MCP and legacy `inputRequests` reply forms. Existing fire confirmation stays in its original handler; legacy boolean confirmation is decoded into that handler's existing response shape. A navigation or recon reply currently returns `UGV_INPUT_HANDLER_NOT_AVAILABLE` without a Device call, rather than passing through fire confirmation. Mixed legacy and MCP reply arrays are rejected. This is a verified local reply route and a fail-closed boundary, not a RequiredInput generator or a working recon decision handler. NPC Tank keeps the prior `updateFire` fallback.
