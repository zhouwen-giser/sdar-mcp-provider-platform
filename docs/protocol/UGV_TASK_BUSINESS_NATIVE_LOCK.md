# UGV recon visual lock observations

For requested Actions initiated by the new Provider policy, see
[Provider automatic visual lock](UGV_TASK_BUSINESS_PROVIDER_AUTO_LOCK.md).
That path requires journal dispatch plus a later stage-3 observation before
activation. The device-observation path described below retains its existing
unknown-origin semantics. Production automatic ownership remains unqualified.

The Runtime reads only accepted, non-retained `/ugv/area_recon/status` messages with an explicit recon mission ID. It requires exactly one active `vehicle_area_recon` Execution owning that mission and a status time after Task creation. The 2026-09-28 live status stream omitted that ID throughout a lock cycle, so this production gate did not receive a qualified Task-bound source. For qualified facts, `NativeLockBusinessProcessor` persists one `sensor.visual_lock` Action per observed lock cycle in the Execution's Context; it has no Device MCP client and makes no lock Tool call. Existing standalone `vehicle_track_target` resource events remain on their original path.

If the Execution later has a replacement mission, old mission lock stages cannot create or change its current Action. A mission switch alone does not prove physical release of the prior lock; the true release and resume timeline still needs source qualification.

Stage 2 records `locking`, and stage 3 records `observing`. A first observed stage 3 creates an active Action with `startedAt` set to that observation and no `requestedAt`. The actor is the device, while `triggerOrigin` remains unknown because the status feed does not identify who initiated the lock. The Action records the source target ID, mission session and stage. When the matching `target.object` is available, `subjectRefs` pins its Artifact revision; a subsequent status can add this reference if the status arrived first. A different target ID terminates the prior Action with `VISUAL_LOCK_REPLACED` and starts a new Action. Repeated same-stage status does not make another Action.

Target association uses the latest version of each matching target object. Its capture time must be no later than the lock status observation; an out-of-order status cannot cite a target version observed in the future. A later eligible status can add that reference. A previously visible but now lost target is not linked to a newly observed lock, and a source target ID shared by multiple sensor namespaces remains unlinked. The raw lock stage is still recorded; the Provider does not infer target visibility from it.

Stage 1 closes an active Action. Recon mission status 11 yields `OBSERVATION_ENDED`, 10 yields `RECON_FAILED`, and 9 yields `RECON_INTERRUPTED`; other motion states use `VISUAL_LOCK_END_CAUSE_UNKNOWN` rather than claiming release or loss. Stage 4 is reported as `recon.lock.stage_4_unqualified` in Context phase and does not infer loss or completion. Stage 4 and targetless stage 2/3 observations advance the mission's source clock without creating, changing or ending an Action. A later delayed stage cannot move an Action backward across that observation. The mission phase uses `recon.scanning`, `recon.locking`, `recon.observing`, or `recon.resuming` where those source states are known. Lock state is separate from target visibility and Task lifecycle. A command ACK never establishes active lock.

The first stage-1 scanning observation also establishes a mission-scoped source time when no Action exists. It does not create an Action or public Action event. A delayed older stage 2 or 3 cannot then open a lock that predates the observed scanning state. Later same-phase or additional scanning observations advance the Context source clock without a redundant Action event; a newer qualified lock stage can still start an Action. Distinct cursors with the same observed time have no proven order and cannot change the current Action; a later source time is required. The current source cursor is bound to its stage, target, motion status and observation time, so changed content at that cursor is rejected.

The recon Profile advertises the observed Action type but keeps `visualLockOwner: disabled` and `automaticVisualLock: not_supported`. In one live continuous scan with target `9` visible, no automatic stage 2/3 appeared during the eight-second observation window. An explicit `ugv_area_recon_lock(true, 9, mission_id)` call then produced stage 3 and paused scanning. With a five-second lock-duration limit, stage 1 returned and status resumed scanning without a separate release call. A second live run called `ugv_area_recon_lock(false, 0, mission_id)` after manual stage 3; the ACK was followed by stage 1 and scanning status 5. These prove device-layer manual lock and two release/recovery paths, not automatic lock ownership, a source lock session identifier, or a Task-bound Provider Action. Both status streams had no mission ID, and each own-run stop left the device unlocked and stationary. Automatic ownership, session/reset rule, loss behavior and stage 4 meaning remain external qualifications (`EXT-UGV-NATIVE-LOCK`, `EXT-UGV-RECON-CORRELATION`).
