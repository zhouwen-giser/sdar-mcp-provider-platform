# UGV task business discovery (`1.0-rc2` development)

`OperationDefinition.businessFeedbackProfile` is an optional Proto `Struct` field. The Adapter sends it per Operation, and `OperationRegistry` validates it before projecting `io.sdar/taskBusiness` into that Operation's tool `_meta`. The profile is absent for all Operations by default, including current UGV navigate/recon. It is never a Provider-wide boolean. The extension does not add a device Operation or change existing `vehicle_navigate` or `vehicle_area_recon` inputs.

An advertised profile requires its `vehicle.business` source in the same Manifest with durable replay, plus the declared read and command methods. It lists only object types the Operation can actually produce; it separates those static capabilities from each Task's current Context/availability. Route adoption, footprint, automatic visual lock and running replanning may be listed only after their individual qualification. The optional `methods.snapshotPartGet` declares that this Operation's Adapter supports bounded exact Context/object-version reads for snapshot descriptors. Older profiles may omit it; Runtime then omits the method from public discovery unless another Operation declares it, rejects a direct part read for the unsupported Task, and fails a descriptor-only Context page explicitly instead of issuing an unsupported private RPC. The Registry refuses a profile with a missing/non-durable source, a synchronous Operation, an unsupported contract version, or contradictory method/type declarations. The `1.0-rc2` schema is generated at `protocol/task-business/v1/operation-profile.schema.json` from `packages/adapter-protocol/src/task-business-profile.ts`.

`UGV_TASK_BUSINESS_PROFILE_PATH` optionally points to a local JSON settings file validated by `UgvTaskBusinessSettingsSchema`. It covers lock owner, decision mode, wait timeout and dismiss/expiry policy, coordinate frame/transform, trajectory summary, footprint/coverage mode, plan-adjustment switches and content mode/inline size. The checked-in example is disabled. When enabled, startup requires a PostgreSQL Provider Store and an installed native business schema, or the verified GOWM owner schema when shared storage is selected. Startup does not create missing tables. The enabled settings alone do not assert any device capability.

`businessFeedbackProfile` is optional in the shared Adapter type/Proto. NPC Tank and Home Assistant manifests omit it and retain their existing behavior. Contract tests use a clearly synthetic fully qualified profile to verify Proto transport and Registry projection; that fixture is not evidence that the selected GOWM simulation has route adoption, footprint, lock or replanning capability.

The Adapter Proto now has additive `GetBusinessContext`, `GetBusinessSnapshotPart`, `GetBusinessArtifact` and `ApplyIntervention` RPCs, plus optional `UpdateExecution.business_input_command` at new field 5. Existing task-control field numbers and Adapter protocol `1.0` remain unchanged. The business RPCs are private Adapter/Runtime transport; they are not methods in the official MCP `tasks/*` namespace. `GrpcAdapterGateway` encodes command JSON through protobuf `Struct`, decodes page/Artifact data and returns actual content bytes when requested. Artifact and snapshot-part bytes use offset and bounded chunk fields; the server emits at most 1 MiB per response and a next offset until complete. `VehicleProviderGrpcServer` dispatches these only when its Runtime supplies the corresponding business handlers and otherwise returns `UNIMPLEMENTED`.

`task-business:check` also compares the current parsed Adapter Proto with the frozen legacy structural surface in `protocol/task-business/v1/legacy-adapter-surface.json`. It requires every old RPC signature, message field number/name/type/presence, enum value and reservation to remain, while allowing additions. The fixture comes from the UGV v1 protected Proto hash. This is structural wire compatibility evidence; it does not prove every old client's behavior or replace Runtime tests. The historical UGV v1 `protected-check` still requires the original file hash and therefore fails after these authorized additive fields; its lock is left intact.

The public `io.sdar/taskBusiness/interventions/apply` extension is now registered in Runtime outside the official `tasks/*` namespace. `server/discover` advertises its method and request/result schemas only when an Operation has a validated Profile with `methods.interventionApply=true` and a nonempty `interventionTypes` list. The selected UGV read-only Profile does not meet that condition, so discovery omits the method and calls fail closed. The synthetic local Profile used to test HTTP → PostgreSQL Task command → private gRPC mock transport is not a selected UGV capability or evidence of plan adoption.

UGV Runtime explicitly returns a bound negative `ApplyIntervention` Ack if a stale, previously qualified Runtime Task reaches its private gRPC method. It validates a new command's schema, Task/Execution binding and responder before reserving the command sequence; an already reserved sequence replays its prior Ack. This is a terminal rejection for unsupported or nonrunning UGV execution, not a capability advertisement or a business result. The selected read-only Profile and its missing real replan/adoption source are unchanged.

The UGV startup path now injects the Context query service. New navigate/recon Executions initialize revision 1 Context before device dispatch. Historical Executions without the persisted business marker return `BUSINESS_CONTEXT_NOT_AVAILABLE`; a failed initialization records a terminal technical failure before dispatch. With an enabled, qualified PostgreSQL source, the Manifest advertises an operation-level **read-only** profile for navigate/recon: Context/Artifact reads and durable business events are available. Navigate declares requested destination/waypoints and observed trajectory; recon declares requested area, coverage plan/current coverage, observed target objects/tracks and observed `sensor.visual_lock` Action. Real adopted route, calibrated footprint, automatic-lock ownership and runtime replanning remain `not_supported`. Required Input and Intervention methods/types remain disabled. Runtime startup requires `BUSINESS_EVENTS_ENABLED` when any business profile is advertised, so it cannot claim `eventsListen` while public event ingestion is disabled. Selected GOWM storage cannot pass this startup gate until its owner schema is installed and verified. Local mock device tests and native isolated PostgreSQL tests do not establish selected-profile simulation or SDAR public integration acceptance.

## Startup qualification of configured policy

`UGV_TASK_BUSINESS_PROFILE_PATH` remains opt-in. When enabled, startup checks the configured policy against the currently wired read-only UGV business Profile before opening the business Store. Only device-reported coverage with lock, decision, footprint and adjustment modes disabled is accepted at this checkpoint. Other configured modes fail with a specific `UGV_BUSINESS_*` reason instead of being silently ignored while the manifest advertises a different policy. The selected device-native automatic-lock development target still requires native lock qualification and implementation of the applicable input/adjustment paths.

The current trajectory projector follows every accepted mission-bound position observation and does not use `trajectory.sampleEveryMs` as a throttle. The settings schema retains this field for the development target; startup accepts only its fixed example value and rejects other values. Likewise the Input and content policy fields cannot be tuned at this read-only checkpoint. These fixed values do not qualify the unavailable Input or Intervention methods.
