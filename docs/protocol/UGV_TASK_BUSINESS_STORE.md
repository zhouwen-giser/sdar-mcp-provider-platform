# Task business Store port and Memory semantics

`TaskBusinessStore` in `packages/provider-adapter-kit/src/task-business-store.ts` is the common port for Context snapshots, exact object versions and business command records. `BoundExecutionScope.fromExecution` takes an already admitted Provider execution. Its key includes Task/Execution, Provider/resource/Operation, authorization hash, normalized execution mode, simulation ID and, when present, the GOWM device/data scope/binding/service/source session. The simulation ID is the scene boundary currently available in the Provider execution record. A separate device scene identifier has not been established locally; a caller must not infer it from untrusted request JSON.

`MemoryTaskBusinessStore` implements the port for component use. `commitChangeSet` compares the current Context revision, validates the next Context and every object version, rejects overwrite or revision gaps, checks that every Context reference exists and that active references are listed, then replaces the per-scope aggregate in one synchronous step. Action, Required Input and Intervention revisions use their transition guards. An accepted command is claimed once by command ID and canonical request hash; an Input reply also records a canonical response hash. A caller-resolved Input version must match both that command ID and response hash before its Context revision commits. A terminal record cannot change the response hash. Exact old versions remain addressable in the same scope. A Context may be created before a Runtime Task row exists because this Store does not depend on that row.

`PostgresTaskBusinessStore` implements the native Provider database port using migrations `030_task_business_versions.sql`, `031_task_business_command_fences.sql`, and `032_task_business_content.sql`. Context writes, object-version inserts, immutable content bytes and terminal command records share one transaction and a per-scope advisory lock. A Context snapshot reads its referenced versions in a repeatable-read transaction. The Store does not require a Runtime Task or Provider execution row to create Context. Migration execution remains an explicit owner operation; Store startup does not run DDL.

`claimCommand` serializes command-ID, semantic entry and Runtime command-sequence reservations for one bound scope. New native migration `031_task_business_command_fences.sql` adds unique expression indexes for those last two identities. A failed terminal command frees the semantic entry; its Runtime sequence remains reserved so an old dispatch cannot be reinterpreted. Terminal writes must preserve the original entry key and sequence. The GOWM owner template includes the same indexes, but the owner installation has not been verified.

`commitBusinessChangeSet` adds typed `vehicle.business.changed` feedback to the same Context/object/command transaction. Its PostgreSQL path allocates source sequence, writes source waterline and log in that transaction, and returns the committed event identities. Multiple events may share a Context revision while retaining separate source IDs/sequences. A `CONTEXT_FINALIZED` draft must exactly match the committed final Context revision, summary, Artifact and Action references, and finalization time; an inconsistent draft cannot commit a Context or source event. The Hub's `notifyCommittedTaskBusinessEvent` only wakes subscribers after commit; the normal append path refuses this source. The durable source is enabled only after business Store startup succeeds, and a read-only business Profile is advertised only when that source is qualified. GOWM uses a service/session-specific storage source key while the public source ID stays `vehicle.business`; real shared-schema behavior remains untested pending owner installation.

Every committed Context revision keeps `updatedAt` at or after the previous revision's time. Memory and PostgreSQL reject a backward timestamp before publishing Context, object versions or source events. Individual Artifacts and feedback may retain an earlier source observation time when delayed facts arrive; the Context clock is the scope-wide high-water mark rather than a replacement for those source timestamps.

`getArtifactVersion` reads an exact revision; `getArtifactLatest` resolves the highest revision in the bound scope. `readArtifactContent` performs identity, availability and expiry preflight. `readArtifactContentBytes` returns copied bytes for the main content or a named representation, checking the stored media type, length and SHA-256 against the selected Artifact version. A new `content_ref` requires matching bytes in the same change set; missing, extraneous, conflicting or mismatched bytes reject the whole commit. References never fetch caller URLs or recursively return another `content_ref`. Expired content returns `ARTIFACT_CONTENT_EXPIRED` even while its immutable Artifact metadata remains readable. Expiry is a logical read cutoff; physical byte deletion is not automated by this Store.

`getContextSnapshot` has an explicit 1 MiB response bound and reports `BUSINESS_SNAPSHOT_TOO_LARGE` rather than truncating. `getContextSnapshotPage` returns exact object versions or descriptors that point to `getObjectVersion`; an oversized Context gets a `getContext` descriptor. Each page, including its cursor, fits the requested 1 KiB–1 MiB bound. Cursors bind the scope and Context revision, and a changed revision fails instead of combining pages from different Contexts. `finalized` requires `finalizedAt` and an empty `activeRefs` map, retains historical object references, and rejects later Context writes. Finalizing Context neither changes Action state nor asserts that a physical target lock was released or that the Runtime Task reached terminal state.

The Memory implementation is not selected as a new live-mode fallback. The native PostgreSQL tests ran against a temporary isolated PostgreSQL 16 container; they do not qualify GOWM shared storage, actual SDAR wiring or selected-profile simulation.
