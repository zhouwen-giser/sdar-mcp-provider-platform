# UGV reconnaissance business mapping

An admitted area scan stores `recon.area` as a requested `OGC:CRS84` polygon. A circular scan has no polygon request. Both modes start with separate `recon.coverage_plan` and `recon.covered_area` Artifacts marked `not_produced_yet`; neither is inferred from the configured region. The current UGV interface does not publish a scan plan, so `activeRefs` contains no effective scan plan.

The Runtime requires an exact `/ugv/area_recon/status` message with a mission ID and `motionStatus` before strict binding to the persisted Execution and its post-dispatch status cursor. In the 2026-09-28 live scan, the status messages had no `mission_id` or `id`, including during scanning, visual lock and release. The current production gate therefore cannot project those live messages into a Task Context. With a qualified mission-bound source, `ReconBusinessProcessor` updates the Context phase from `motionStatus`, not from chassis MissionState. If the _same status message_ includes coverage percent or counts, it records them in `summary.properties.reconCoverage`, with the effective `areaRevision`, source time and an `ARTIFACT_CHANGED` event. The `recon.covered_area` Artifact remains `unavailable` while the source has no usable grid frame and origin. Its earlier versions remain readable.

A fresh status without a mission ID clears any ID retained in the merged vehicle snapshot. A status with a different mission ID also clears the previous mission's progress, coverage, lock and command/exception fields before applying its own fields. Partial coverage and exception patches do not clear the current ID. This prevents a later unbound target message or poll from inheriting an older mission's correlation; it does not turn the live unbound status into a qualified source.

For an area scan, coverage initially belongs to the exact original requested `recon.area` revision 1. A later requested or candidate area Artifact does not change that basis. An adopted area must be a new available `recon.area` version with `semantics: planned`, named by `activeRefs.reconEffectiveArea`; its `areaRevision` must exceed the exact previous effective area's revision. The Memory and native PostgreSQL Stores require that switch, the incremented effective plan revision, a new `recon.covered_area` version marked `not_produced_yet` with `COVERAGE_RESET_FOR_NEW_AREA`, removal of the old coverage summary/cursor, and two Artifact changes plus a Context metadata event in one commit. An applied `recon.adjust_area` must name the adopted area and reset coverage as command results; a rejected adjustment cannot switch the effective area. The old coverage version stays readable as history.

The same area switch must clear `activeRefs.currentFootprint`: its previous `areaRevision` cannot remain the current view after adoption. The old footprint Artifact remains readable in history, and a new area-bound source fact may publish a new active footprint after the switch. A switch that retains an active footprint rolls back with `RECON_AREA_ADOPTION_FOOTPRINT_STALE`.

After a switch to area revision 2 or higher, a coverage fact must carry a source-verified `areaRevision` matching the adopted area. Older revisions are ignored and future revisions rejected; an unbound status counter cannot become coverage for the new area. The selected status topic has no area revision, so Runtime suppresses its coverage counters whenever an effective-area ref is present, while continuing to process the same message's mission status. No selected device replan/adoption source or effective-area writer is wired. Therefore this contract and its synthetic tests do not qualify a real running area adjustment or post-adjustment coverage. A qualified source must provide adoption and area-bound coverage with its denominator before that path can be enabled.

Only the Execution's latest downstream mission can update its current recon Context. Facts captured before Execution creation or from an earlier mission are rejected by the processor; Runtime also filters earlier missions before dispatch. Status and coverage duplicate markers include the mission ID, so a replacement mission with the same phase or source cursor produces a new observation. Older status timestamps within the current mission cannot rewind its phase. This is a local observation fence; the current Profile has no qualified real replacement mission or scan-plan adoption path.

Status and coverage observations retain their own source timestamps in phase and coverage metadata. If different observation types arrive out of order, the Context's `updatedAt` keeps the latest committed observation time; a valid delayed status or coverage fact cannot move it backward.

The authoritative Provider Task state likewise ignores an exact status whose mission ID belongs only to the Execution's history. A synthetic two-mission Runtime test confirms a late old-mission terminal report neither ends the Task nor overwrites its reason, while the current mission's terminal report still applies. The selected UGV source has no qualified mission replacement path, so this test is a local state guard rather than simulation acceptance.

The standalone `/ugv/area_recon/coverage` topic contains `runId`, counts, optional `coveredCells` and cell size, but no mission ID or defined grid origin/frame/index convention. The 2026-09-28 live finite scan emitted `run_id: 1`, `covered_n: 424`, `total: 424`, and 424 coordinate pairs in `covered`, while the MCP mission ID was a different value. Those pairs look like local positions; the publisher did not declare their frame, origin, axis convention, or whether they are cell centers rather than indices. This source is not attached to every active Task on the vehicle. To publish geometry, a verified source must supply task or run ownership and a declared grid or coordinate frame with denominator. The processor's framed grid path can derive local MultiPolygon cells from a qualified fact; current device data does not satisfy that path. If cells are missing, incomplete or exceed the bounded geometry size, the Artifact remains unavailable and statistics remain available. No requested polygon is ever presented as observed coverage.

Within one mission-bound coverage observation, covered and sector counts cannot exceed their reported totals. A supplied grid denominator must equal the reported total cell count even when cell geometry is absent. The covered count also cannot exceed that denominator when the total count is omitted. A framed cell list must contain unique indices and cannot contain more cells than the denominator, including when it is too large to render as geometry. Reported cell size must match the supplied grid even without renderable cells. A complete cell list must match a reported covered count even when it is too large to render; `incomplete=true` identifies a partial list that is not used as the full numerator. When a percent and complete numerator/denominator are present, the percent must agree with their ratio within one percentage point to allow source rounding. For a grid, the denominator can supply a missing total count, and a complete cell list of at most 100 cells can supply a missing covered count. Contradictory observations are rejected before they can replace the Context summary or covered-area Artifact; a valid rounded source value is retained as reported rather than recalculated.

The coverage source-cursor signature uses canonical object keys and treats covered cell indices as an unordered set. Replaying the same source cursor with cells in a different order is a duplicate; changing the actual cells, counts, grid or observation time remains a source-cursor conflict. Within the same mission and effective area revision, a distinct cursor at the same observed time has no proven order and cannot replace already recorded coverage statistics or geometry. A later source time can advance them; a new adopted area starts a separate clock after its required coverage reset.

The read-only recon Profile advertises requested area, explicit scan plan absence, device-reported coverage statistics, observed targets and observed `sensor.visual_lock` Actions for qualified mission-bound facts. It does not advertise a current footprint or qualified automatic visual-lock ownership. `EXT-UGV-RECON-CORRELATION` records the live status/target/coverage mission-binding gap, and `EXT-UGV-COVERAGE-GRID` records the grid frame contract; footprint calibration and native-lock qualification are tracked separately. Component tests use synthetic mission-bound facts and a local MQTT/Runtime fixture. The live device scan is separate device-layer evidence, not Provider or SDAR integration.

During exact status messages with native lock stage 2 or 3, aggregate coverage counters are not promoted to scanning progress for the same EO sensor. Runtime first projects the native lock transition, then coverage; the coverage processor also suppresses updates while a visual-lock Action remains active. A stage-1 release removes that Action before a same-message coverage observation is considered, so subsequent measured scan progress can resume. Stage 4 remains unqualified and does not establish release. This conservative local rule prevents double counting in the selected single-sensor profile; the real device's automatic lock/loss/resume timeline and grid geometry still require external qualification.

Within one mission, native lock facts retain a source-cursor signature and latest observed time in Context summary properties. The same cursor with changed stage, target or time is rejected; an older stage cannot reopen an Action after a later release. A first stage-1 scanning observation establishes the source clock even when no Action existed, so an older delayed stage cannot invent a lock. A stage-4 or targetless stage-2/3 observation has no qualified Action meaning but still advances that clock without creating or ending an Action. A newer observation of the same phase advances this durable source clock without a new Action or public Action event, so an older different phase cannot move the current lock backward. Distinct same-time cursors have no proven order and cannot replace a known lock or recon phase; a later source time is required. An additional release after the Action has closed advances the clock silently. These are local source-order guards, not proof of device-native lock ownership or real release behavior.
