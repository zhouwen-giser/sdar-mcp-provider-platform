# UGV navigation business source mapping

`vehicle_navigate` creates a requested `navigation.destination` Point for a point mission or a requested `navigation.waypoints` MultiPoint for a route mission. The source is the persisted admitted Task arguments. `distance` and `return_home` do not contain an explicit destination or ordered waypoints, so initialization creates only the Context. Requested geometry is not a planner route and never sets `activeRefs.route`.

`NavigationBusinessProcessor` defines the inbound projection for a _verified_ planner fact. The fact must name the persisted Execution's **current** mission, a route ID and source revision, a source record and planner, adoption state, observation time no earlier than the Execution, and actual LineString or MultiLineString content. A fact from a prior mission retained in the Execution's mission history cannot replace the current effective route. GeoJSON declares `OGC:CRS84`; local geometry declares frame, unit, axis convention and optional transform reference. The processor stores planned `navigation.route` revisions with source and mission provenance. A candidate adds a route version and immediate Artifact event but keeps the active route. A confirmed adoption updates `activeRefs.route` and `effectivePlanRevision`, and emits Artifact and adoption business events after the atomic store commit. Duplicate source versions do not create another version; same-version content/provenance conflicts fail. Earlier adopted versions stay readable.

Current southbound mapping is **unwired**. `ugv_path_follow_mission` sends `task_points`, `need_plan`, and `density`; its validated result is a mission receipt and has no route geometry or adoption fact. On 2026-09-28, a live `tools/list` described a `/ugv/planned_path` publisher after planning. A planning call for a user-supplied destination returned a six-point, 148.5 m route receipt in the unstarted state, but an exact MQTT subscription received no `/ugv/planned_path` message during the call or following 2.5 seconds. The Provider does not currently subscribe to that topic. The payload, mission binding, route revision, and adoption semantics therefore remain unverified. The newly created mission was terminated before start; the vehicle did not move. A mission ACK, target point, current position or observed trajectory is insufficient to claim route adoption. Once a qualified planning run yields an actual route source and adoption fact, bind them to the persisted Execution mission ID and provide a dedicated event path with no trajectory sampling throttle. Until then the navigation Profile advertises only requested destination/waypoints and `routeAdoption: not_supported`. The external input contract is tracked as `EXT-UGV-ROUTE` in the Goal package.

The processor component tests use synthetic `NavigationPlanFact` values. They validate local versioning and events; they do not demonstrate actual UGV planning, simulation or SDAR integration.

## Observed trajectory and terminal archive

`NavigationTrajectoryProcessor` receives only exact MQTT positions accepted by ingress authority gating. Runtime binds each nonretained `/ugv/gnss` or `status/ugv1` position to one active `vehicle_navigate` Execution using the current mission ID, a fresh mission authority and observation time after Execution creation. A position received before that binding, for another mission, or with a stale mission authority is not attributed to a Task. The processor persists a source cursor hash and UTC observation time in the Context, deduplicates repeats and rejects conflicting same-time positions.

The Provider's authoritative navigation Task state now also ignores a late status from a mission retained only in the Execution's history. A synthetic two-mission Runtime test confirms that a prior mission failure cannot terminate the Task after the current mission changes, while a failure reported by the current mission still can. This is a current-mission state fence for future replacement flows; it does not create or verify a real mission replacement or adopted route.

The first measured point is an observed `navigation.trajectory` Point with `sampleCount=1`. A second changed point within the configured chassis freshness window converts that segment to a LineString. Stationary samples advance the persisted observation clock without publishing a duplicate geometry revision. A longer source gap or the 256-sample segment bound starts a new Point segment; the prior segment remains referenced and every version remains available by exact Artifact read. Trajectory updates do not advance `effectivePlanRevision` and never set `activeRefs.route`.

After the Provider Execution reaches any terminal state, `UgvTaskBusinessContextService` atomically finalizes the Context, clears active refs, retains Artifact and Action history, records the original execution state and reason code, and emits `CONTEXT_FINALIZED`. Nonartifact active refs are recorded as unresolved in the summary rather than being described as successfully completed. Repeated finalization is idempotent. Public reads can also complete a pending finalization after a process interruption.

Local gRPC wire tests use a controllable Device MCP double and an explicitly synthetic planner adoption fact to check adopted route, trajectory, active refs and exact Artifact reads. Native PostgreSQL tests reopen the Store and read trajectory versions and the terminal summary. These tests establish local behavior only; the live planning receipt is not a route/adoption message, and the selected GOWM/SDAR and actual simulator Task runs remain unverified.
